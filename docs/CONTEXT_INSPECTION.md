# 歷史 Context Inspector 與私密文本

> **先說結論：**歷史 Context Inspector 可能顯示完整故事、角色設定、場景規劃與修訂前草稿。預設會把實際送給文字生成 provider 的 `system` 與 `user` 訊息原文保存在本機 SQLite 資料庫；資料庫備份也會包含這些內容。請把資料庫與備份視為私密原稿保管。

本文件適用於 Story Studio 的故事生成與修訂 run。它說明 Inspector 能證明什麼、資料存在哪裡，以及如何降低未來 run 的原文留存量。

## 「實際送給 provider 的訊息」是什麼

每次故事生成或修訂都會先把選定的不可變版本、角色 Canon、場景規劃與使用者指令渲染成一個單輪請求：

- `system`：模型必須遵守的生成或修訂契約。
- `user`：組裝後的場景 context、規劃資料與生成要求；修訂 run 還會包含要修改的來源草稿全文。

Inspector 所稱的「當時實際送出的訊息」，只指這兩個最終字串的 UTF-8 位元組內容。它不表示模型的隱藏推理、provider 的 HTTP 標頭、provider 內部狀態、原生傳輸格式或模型輸出可以由 Inspector 重建。生成結果與部分草稿由其他 run／draft 欄位保存。

這兩段文字可能包含完整私密故事、角色資訊、成人內容、提示詞與使用者指令；不要把 Inspector 畫面、資料庫或備份當成可公開分享的診斷資料。

## 原文何時寫入

應用程式完成 context、版本歸屬與成人資格等前置驗證後，會先建立並提交一筆 `RUNNING` 生成紀錄，再進行 provider I/O。當原文儲存設定為開啟時，該紀錄同時保存 `system` 與 `user` 原文。因此：

- 成功、失敗、逾時或取消的 run 都可能留有完整原文；是否有模型輸出不影響這件事。
- 程序在 provider 呼叫期間中斷時，先前已提交的 run 仍可能留有原文。
- 若錯誤發生在生成紀錄建立前，例如 context、版本歸屬或資格驗證失敗，則不會為該次嘗試新增這種原文紀錄。

只有原文同時通過既存 SHA-256 與 UTF-8 位元組大小檢查時，Inspector 才會稱它為當時的精確訊息。

## 預設值與停用方式

程式設定的預設值是：

```text
store_rendered_generation_messages = true
```

若要停止**未來 run** 的 provider 訊息原文留存，請在專案根目錄的 `.env` 設定：

```dotenv
IMF_STORE_RENDERED_GENERATION_MESSAGES=false
```

儲存 `.env` 後，完整停止並重新啟動 Streamlit 應用程式，讓設定與服務容器重新載入。只重新整理瀏覽器頁面不應被視為完成重啟。可在 Story Studio 的隱私說明區確認目前工作階段讀到的設定。

停用後仍會為每個新 run 保存：

- `system` 與 `user` 的 SHA-256；
- 兩段訊息各自的 UTF-8 位元組大小；
- 不可變輸入快照、版本來源 ID、生成選項與其他稽核 metadata；
- 生成結果或部分草稿（若有）。

SHA-256 是單向完整性證據，不是可用來取回原文的備份；位元組大小也不能還原內容。

### 只影響未來，不會清洗歷史

把設定改為 `false` 不會重寫、刪除或遮蔽既有 run，也不會修改舊備份。歷史紀錄中已保存的原文仍會存在並可供 Inspector 驗證。若日後再改回 `true`，則從重新啟動後的新 run 起恢復原文留存。

## Inspector 的四種顯示模式

Inspector 使用以下固定繁體中文標籤；標籤本身就是誠實性界線：

| 模式 | 畫面標籤 | 可以主張的內容 |
| --- | --- | --- |
| A — `stored_exact` | **當時實際送出的訊息（已儲存）** | 資料庫中有 `system` 與 `user` 原文，且兩者的 SHA-256 與 UTF-8 位元組大小都通過驗證。這是唯一稱為當時原文的模式。 |
| B — `reconstructed_match` | **由不可變快照重建；SHA-256 與原始訊息相符** | 原文未儲存；以 run 鎖定的不可變版本重建候選字串，輸入快照也通過驗證，而且兩個候選字串的 SHA-256 都與 run 紀錄相符。這證明重建位元組相符，但畫面不把候選文字冒稱為「已儲存原文」。 |
| C — `reconstruction_mismatch` | **無法以目前渲染器逐位元重現；原始 SHA-256 已保留，但當時的原文未儲存** | 找不到必要歷史來源，或以目前程式重建的候選字串／輸入快照無法通過完整性比對。診斷候選不是歷史原文，不得引用為當時實際請求。 |
| D — `stored_integrity_error` | **已儲存的原文未通過完整性驗證，不能視為當時的原文** | run 標示有儲存原文，但文字缺失，或 SHA-256／位元組大小不符。可能是資料損壞或遭修改；畫面只可供診斷，不能宣稱精確。 |

模式 C 與 D 都是 fail-closed 結果：應保留警告，不要把診斷候選複製成所謂歷史原文，也不要手動修改資料庫來消除警告。

## 本機優先、遙測與 provider 網路界線

Imaginarium Forge 沒有獨立的產品遙測、雲端同步或自動故事上傳流程，也不會自動上傳資料庫或備份。預設 `IMF_OLLAMA_BASE_URL=http://localhost:11434`，因此預設生成請求留在本機 loopback 端點。

但「沒有遙測」不等於「任何設定下都不會傳出文本」。按下生成時，應用程式必須把上述 `system` 與 `user` 訊息送到你設定的 provider endpoint：

- 若 `IMF_OLLAMA_BASE_URL` 被改成遠端主機、反向代理、容器外服務或第三方服務，完整訊息會離開本機並傳到該 endpoint。
- 遠端 provider 的保存、日誌、訓練與刪除政策不由本應用程式控制；使用前應自行審查。
- 對敏感文本應優先使用可信任的本機 endpoint；若必須跨網路，應使用受信任且加密的連線與存取控制。

這種 provider 請求是使用者配置的生成資料流，不是產品遙測。

## 日誌規範

正常應用程式日誌不得記錄完整 `system`／`user` 訊息、完整故事或 provider response body。日誌只應包含狀態、識別碼、計時與經過節制的錯誤摘要；原文的受控檢視位置是本機資料庫與 Inspector，而不是 stderr 或日誌檔。

新增除錯、provider adapter 或反向代理時也必須遵守此規範。若自行啟用 HTTP body tracing、封包擷取、代理存取日誌或第三方診斷功能，這些外部工具可能另行留存文本，且不受本應用程式的原文儲存開關控制。

## 資料庫成長

啟用原文留存時，每個生成與修訂 run 都會各保存一份完整 `system` 和 `user` 字串。重複使用相同大型 Story Bible、角色 Canon 或來源草稿仍會在不同 run 中重複佔用空間；實際 SQLite 檔案成長還包含資料頁、索引與交易開銷，因此不會只等於 Inspector 顯示的兩個位元組大小總和。

停用原文留存可降低未來 run 的增量，但 hashes、快照、metadata、草稿與輸出仍會成長。SQLite 的 `-wal`／`-shm` sidecar 也可能在程式運行期間存在；完整備份則會複製資料庫當時可見的全部內容。可從 System Health 頁確認目前資料庫與備份路徑並監控備份大小。

## 備份與還原的隱私含義

- SQLite 線上備份會包含資料庫中的完整故事、提示詞、已儲存 provider 訊息、hashes、草稿與稽核資料。備份不是去識別化版本。
- 還原前會先驗證指定備份，並為目前資料庫建立 `pre_restore_*.db` 安全備份；指定備份與安全備份都要視為同等敏感。
- 還原較舊備份可能重新帶回已從目前資料庫狀態中消失的歷史文字。環境變數設為 `false` 仍只約束還原後產生的新 run，不會清洗被還原的歷史原文。
- 只刪除或覆寫目前資料庫，不會刪除 `data/backups`、pre-restore safety backups、使用者另行複製的檔案、下載的匯出檔或遠端 provider 的紀錄。
- 不要把資料庫、備份、錯誤重現包或含原文的截圖提交到 Git、公開 issue、一般雲端同步資料夾或未加密的共用媒體。請使用作業系統權限與磁碟加密保護資料目錄。

## 封存、完整刪除與資料殘留

目前 UI 支援的是專案**封存／還原**，沒有單一專案 hard delete。封存只是狀態變更，不會移除該專案的故事、prompt、run 或 provider 訊息。所有專案共用同一個 SQLite 資料庫，因此目前沒有受支援的方法只永久刪除其中一個專案而保留其他專案。

若你的目標是刪除這個資料庫中的**全部本機專案**，請使用以下明確、使用者控制的程序：

1. 在 System Health 頁記下畫面顯示的「資料庫」與「備份目錄」實際絕對路徑。預設為 `data/imaginarium_forge.db` 與 `data/backups/`；若設定過 `IMF_DATA_DIR`，不要假設仍是預設路徑。
2. 完整停止 Streamlit 與所有 Imaginarium Forge 程序，避免仍有 SQLite 連線或交易。
3. 確認目標是剛才記下的精確資料目錄，而不是工作區根目錄、使用者家目錄或其他廣泛路徑。
4. 刪除精確的資料庫檔 `imaginarium_forge.db`，以及同目錄中存在的 `imaginarium_forge.db-wal`、`imaginarium_forge.db-shm`。
5. 若也要移除可恢復副本，刪除畫面所列備份目錄中的 `backup_*.db`、`pre_restore_*.db` 與其 manifest。另行檢查並刪除你自己複製的資料庫、下載匯出檔、截圖與其他備份。
6. 再次確認沒有要保留的專案後才執行刪除；這會同時移除所有本機專案，且應視為不可逆。重新啟動應用程式會建立新的空白資料庫。

作業系統的一般檔案刪除不保證在 SSD、快照、同步服務或備份媒體上達到法證等級的安全抹除。若有這類需求，請依儲存裝置與組織政策另行處理。若曾使用遠端 provider，也必須在該服務端依其政策處理紀錄。

## 歷史重建的精確限制

原文未儲存時，重建是**最佳努力的完整性驗證**，不是歷史文字資料庫：

1. 重建只使用該 run 鎖定的 Scene Card、Story Requirement、Story Bible、Outline、Chapter Plan、Character Version 與其他不可變來源 ID；不會改用目前最新版本、目前 accepted pointer 或 UI 當前選項。
2. 相關歷史版本必須仍存在、屬於正確專案／場景，且版本鏈必須一致。任何缺失、跨專案或不一致都會使重建失敗或降為 mismatch。
3. 不可變輸入快照本身的 SHA-256 必須正確，且其中的專案、場景與規劃版本 ID 必須和 run 欄位一致。生成選項快照也會獨立解析與驗證。
4. 重建會使用目前安裝的 renderer／模板實作。run 雖記錄 renderer、context schema、contract 與 budget policy 版本，但不包含一份可執行的舊 renderer；程式或模板變更可能造成逐位元差異。
5. 修訂 run 除規劃版本外，還需要可回溯的產出草稿、父草稿全文與可解析的修訂請求。任一項缺失都無法重建當時訊息。
6. 相符與否只以兩段候選字串的精確 UTF-8 SHA-256（並要求可信輸入快照）判定，不以肉眼看起來相似、語意相同或字數接近判定；換行、空白或 Unicode 位元組差異都會造成不相符。
7. hash 相符只證明候選 `system`／`user` 位元組與已記錄摘要相符；它不重建 provider 原生 HTTP payload、標頭、伺服器狀態、模型權重、隨機執行細節、模型回覆或隱藏推理。
8. 原文缺失且無法重建時，Inspector 仍可顯示已保存的 hashes、位元組大小、來源 ID 與警告，但 hashes 不能反推出原文。

因此，若你需要可直接檢閱且可驗證的歷史輸入，保留原文是最可靠的選擇；若你優先考量資料最小化，可停用未來原文儲存，但應接受部分歷史 run 永遠只能顯示重建相符、重建不符或完整性錯誤狀態。
